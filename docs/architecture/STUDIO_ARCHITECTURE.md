# AI Research & Development Studio Architecture

Version: 0.2
Status: Stabilization Candidate
Last Updated: 2026-08-09

---

# Purpose

This document defines the structural architecture of the AI Research & Development Studio.

The Studio is an AI-native research and development platform.

It is designed to transform signals into researched, evaluated, planned, validated, and recorded outcomes while preserving organizational knowledge.

This document defines the high-level structure.

Runtime execution details are defined separately in:

`docs/runtime/STUDIO_RUNTIME_ARCHITECTURE.md`

---

# Architecture Overview

The Studio consists of five primary architectural layers:

```text
AI Research & Development Studio
|
+-- Foundation
|
+-- Operating System
|
+-- AI Workforce
|
+-- Knowledge
|
+-- Portfolio
```

These layers are connected during execution by the Studio runtime.

---

# 1. Foundation

Purpose:

Defines the long-term identity and principles of the Studio.

Contains:

- Vision
- Mission
- Core principles
- Architectural philosophy
- Long-term direction

The Foundation changes rarely.

Core principles include:

- Problem First
- Core First
- Evidence First
- Validation Driven
- Knowledge Preservation
- Measured Evolution

---

# 2. Operating System

Purpose:

Defines how work moves through the Studio.

The Operating System coordinates the transformation of signals into actionable and recorded outcomes.

Current runtime flow:

```text
Signal
  |
  v
Research
  |
  v
Strategy
  |
  v
Planning
  |
  v
Validation
  |
  v
Review
  |
  v
Task / Knowledge
```

The runtime is coordinated by `StudioOrchestrator`.

---

# 3. AI Workforce

Purpose:

Provides specialized AI-supported capabilities.

Currently implemented workers:

- ResearchWorker
- StrategyWorker
- PlanningWorker
- ValidationWorker

Each worker declares:

- Identity
- Capabilities
- Accepted input types
- Produced output types

Workers are registered through `WorkerRegistry`.

The registry supports capability-based and contract-based worker discovery.

Workers are added only when a validated architectural need exists.

EngineeringWorker and ProductWorker are not part of the current implementation.

They remain possible future capabilities rather than current architectural components.

---

# 4. Knowledge

Purpose:

Preserves information generated by Studio execution.

The current implementation contains two related mechanisms.

## Runtime Knowledge

`KnowledgeWriter` produces `KnowledgeRecord` objects.

These represent knowledge generated by individual runtime executions.

## Persistent Project Memory

`ProjectMemoryStore` persists project execution history.

Stored information includes:

- Project metadata
- Research results
- Opportunities
- Decisions
- Tasks
- Knowledge records
- Execution history

This enables information from previous project runs to be retrieved later.

---

# 5. Portfolio

Purpose:

Represents projects, initiatives, experiments, and future products created through the Studio.

Projects exist independently from the core architecture.

The Studio therefore remains reusable across multiple project types and domains.

Current project execution is represented through:

- Project
- ProjectContext
- ProjectExecutionResult

---

# Runtime Layer

The runtime connects the architectural layers.

Primary runtime components are:

- StudioOrchestrator
- WorkerRegistry
- RuntimeGuard
- ReviewBoard
- TaskManager
- KnowledgeWriter

High-level execution:

```text
Signal
  |
  v
StudioOrchestrator
  |
  +--> ResearchWorker
  |
  +--> StrategyWorker
  |
  +--> PlanningWorker
  |
  +--> ValidationWorker
  |
  +--> ReviewBoard
  |
  +--> TaskManager
  |
  +--> KnowledgeWriter
  |
  v
PipelineResult
```

---

# Research Provider Boundary

Research execution is provider-agnostic.

`ResearchWorker` may operate with:

- Deterministic internal behavior
- An injected ResearchProvider

The current external provider implementation is:

`LMStudioResearchProvider`

This connects to a locally running OpenAI-compatible LM Studio endpoint.

The rest of the Studio architecture does not depend directly on LM Studio.

---

# Runtime Safety

Critical runtime boundaries are protected through `RuntimeGuard`.

It validates:

- Signal
- Required workers
- ResearchResult
- Opportunity
- PlanningResult
- ValidationResult
- Review decision
- ResearchTask
- KnowledgeRecord

Invalid runtime states raise controlled validation errors rather than producing uncontrolled pipeline failures.

---

# Architectural Boundaries

The current architecture intentionally does not include:

- Autonomous signal crawling
- Autonomous worker creation
- Self-modification
- Domain-specific specialization
- EngineeringWorker
- ProductWorker
- Continuous autonomous execution loops

These capabilities require future architectural decisions before implementation.

---

# Compatibility

`studio/workers/strategy.py` currently exists as a compatibility import layer for `StrategyWorker`.

It is intentionally retained during stabilization to avoid unnecessary compatibility breakage.

---

# Decision Model Note

The architecture currently contains two decision-related concepts.

## ReviewDecision

Produced by `ReviewBoard`.

It represents the runtime result of evaluating an opportunity.

## DecisionRecord

Used by `DecisionMemory`.

It represents a stored decision record.

These concepts currently remain separate.

Their possible consolidation is an architectural review item, not a stabilization requirement.

---

# Evolution Principle

The Studio evolves through validated learning.

New capabilities are introduced only when a real requirement emerges.

Complexity must not be added merely because it is technically possible.

The system should remain understandable, testable, modular, and reversible.
